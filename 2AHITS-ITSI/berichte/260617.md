Eine datei ist immer nur eine Folge von Bytes. Ob etwas "Text" ist, hängt von der Kordierung ab. Bei UTF-8 braucht ein ASCII-Zeichen 1 Byte, Sonderzeichen 2-4 Bytes.

# Übung (UTF-8)

UTF-8-Kordierung der Zeichen `🥳😎👽©€ß` ermitteln. Zeichen mit `printf` ausgeben und mit `xxd`die Bytes anzeigen.

Befehl (alles zusammen ist viel übersichtiger):
```sh
printf '🥳😎👽©€ß' | xxd
```

Ausgabe:
```sh
~/workspace$ printf '🥳😎👽©€ß' | xxd
00000000: f09f a5b3 f09f 988e f09f 91bd c2a9 e282  ................
00000010: acc3 9f  
```
🥳 = `f09f a5b3` = 4


😎 = `f09f 988e` = 4


👽 = `f09f 91bd` = 4


©  = `c2a9` = 2


€  = `e282ac` = 3


ß  = `c3 9f` = 2



Emojis liegen im hohen Unicode-Berich und brauchen 4 Bytes, "normale" Sonderzeichen nur 2-3. Das ist das variable Längen-Prinzip von UTF-8.


## Übung (Hex Dump)

### Ausgabe in Binär (0 und 1)
Mit `xxd` über die Option `-b`:
```sh
echo -n "A" | xxd -b
```

Ausgabe:
```sh
~/workspace$ echo -n "A" | xxd -b
00000000: 01000001  
```

`hecdump` hat keine fertige Binäre-Option (nur hex/oktal/dezimal). Für echte 0/1-Ausgabe nimmt man also `xxd -b`.

### octet

Ein octet sind exakt 8 Bit. Der Begriff existiert, weil ein "Byte" historisch nicht überall 8 Bit war. In Standards/RFCs der Netzwerktechnik will man eindeutig sein -> octet = garantiert 8 Bit.

### xxd -E
Zeigt die rechte Zeichenspalte in EBCDIC statt ASCII. Heute praktisch irrelevant, nur noch nötig wenn man Daten von IBM-Mainframes (z/OS) anschaut.

### Dezimalwert als Binärwert in ein File schreiben

```sh
value=65534
printf "%.8x" $value | xxd -r -p > data.bin
```
`printf "%.8x" $value` macht aus der Dezimalzahl einen 8-stelligen Hex-Text (`.8` = vorne mit Nullen auffüllen): aus `65534` wird `0000fffe` (= 4 Byte).

`xxd -r -p` wandelt diesen Hex-Text zurück in echte Bytes (`-r`= reverse, `-p` = plain). Je 2 Hex-Ziffern -> 1 Byte. 

Bytes prüfen:
```sh
od -An -tx1 data.bin
```

Ausgabe;
```sh
~/workspace$ od -An -tx1 data.bin
 00 00 ff fe
 ```

 ### Binärwert wieder als Dezimal (big-endian)

 ```sh
 od -An --endian=big -t u4 data.bin
 ```

 Ausgabe: 
 ```sh
 ~/workspace$  od -An --endian=big -t u4 data.bin
 65534
 ```

 `-An` = keine Adresse, `-t u4` = unsigned Integer mit 4 Byte, `--endian=bit` = höchstwertiges Byte zuerst. Darum liest `00 00 ff fe` als 65534.

 ### xxd -i
 Gibt die Datei als C-Array aus:
 ```sh
 xxd -i data.bin
 ```

 Ausgabe:
 ```sh
 ~/workspace$  xxd -i data.bin
 unsigned char data_bin[] = {
   0x00, 0x00, 0xff, 0xfe
 };
 unsigned int data_bin_len = 4;
 ```
 Anwendung: eine Binärdatei (Bild, Firmware, Zertifikat)direkt in c/c++ -quelltext einbetten, sodass sie mit einkompiliert wird zur Laufzeit keine externe Datei nötig ist.


 ## Übung (Windows Editor)

 Im Windows-Editor eine Datei mit `äüöÄÜÖß€` getippt, einmal als UTf-8 und einmal als ANSI gespeichert, beide in die REPL hochgeladen (nicht im REPL-Editor geöffnet).

 ### cat
 ```sh
 cat utf8.txt
 cat ansi.txt
```

Ausgabe:
```sh
~/workspace$  cat utf8.txt
äüöÄÜÖß€~/workspace$ 
```

```sh
~/workspace$ cat ansi.txt
߀~/workspace$ 
```

Unterschied: Die UTF-8-Datei zeigt alles korrekt, die ANSI-Datei zeigt Mull bei den Sonderzeichen, weil ihre Bytes als UTF-8 interpretert wertden, obwohl sie CP-1252 sind. Standardkodierung der Repl-Kommandozeile ist **UTF-8**.

### Hexdump-Vergleich (Ö, ß, €)

```sh
xxd utf8.txt
xxd ansi.txt
```

Ausgabe:
```sh
߀~/workspace$ xxd utf8.txt
00000000: c3a4 c3bc c3b6 c384 c39c c396 c39f e282  ................
00000010: ac                                       .
```

```sh
~/workspace$ xxd ansi.txt
00000000: e4fc f6c4 dcd6 df80                      ........
```

ANSI nutzt pro Zeichen 1 Byte, UTF-8 mehrere.

### Zeilenumbrüche
Windows benutzt CRLF = `0d 0a` (\r\n), Linux/REPL nur LF = `0a` (\n). Im Hexdump nach `0d 0a` bzw. `0a` suchen.

### Konvertierung mit iconv

```sh
iconv -f CP1252 -t UTF-8 ansi.txt > knov.txt
cat konv.txt
xxd konv.txt
```

```sh
~/workspace$ cat konv.txt
äüöÄÜÖß€~/workspace$ xxd konv.txt
00000000: c3a4 c3bc c3b6 c384 c39c c396 c39f e282  ................
00000010: ac                                       .
```

Nach der Konvertierung werden die Zeichen korrekt angezeigt und sind als Mehrbyte-UTF-8 Kodiert.

### Recherche: ANSI vs. Latin-1
"ANSI" ist unter Windows eigentlich ein falscher Name für Windows-1252 (CP-1252). Latin-1 ist der echte ISO-StandaRD iso-8859-1. Unterschied im Bereich `0x80`-`0x9F`: In Latin-1 sind das unsichtbare Steuerzeichen, in CP-1252 stehen dort druckbare Zeichen wie €, „, ", -, -.
Beispiel: das Euro-Zeichen `€` = `0x80` gibt es in CP-1252, aber nicht echtem Latin-1.
